# PD-RW dual-document handoff｜Forge 只贡献证据与增量更新

PD-RW projects maintain **two** core Markdown files, following the [PD-RW dual-document policy](https://github.com/phr-devil/Problem-Data-Research-Workflow/blob/main/DUAL_DOCUMENT_WORKFLOW.md) and its two templates. RWF is an optional independent DEV evidence/engineering assistant and must not create a competing project diary, machine state, paper plan, or manuscript draft.

## Research record: RESEARCH_RECORD.md

After a meaningful, authorized experiment, valid or invalid DEV Run, informative negative Pilot, bug fix, protocol change, or important decision: supply a short dated/identified entry with task/question, what was actually done, dataset/split/independent unit, evaluator/version, Run or source path/hash, honest positive/negative result, confirmed reason vs hypothesis, reusable assets, next discriminating test and required authorizations. Prior failed paths must remain replayable; NOT_RUN is not a negative result, invalid evaluation is not a scientific refutation. Store raw logs and predictions in their original locations, not Markdown.

## Paper blueprint: PAPER_BLUEPRINT.md

As soon as a paper direction is viable, a pure planning outline may list H1/H2 headings, what each subsection should cover, Claim–Evidence pointers, relevant original papers, contradictory/negative evidence and missing experiments. Only modify an affected subsection after a material change in scientific evidence, Claim or target venue. The blueprint must cite the research record and actual EXP/Run/Claim evidence rather than duplicate and polish model scores; unverified findings stay PLANNED, UNKNOWN or EXPLORATORY. No fabricated numeric results, figures, references or manuscript prose.

## Timeline, permissions and handoff

Project begins / resumes → update RESEARCH_RECORD after meaningful work → once scientific positioning exists, build or update PAPER_BLUEPRINT H1/H2 → source changes update the impacted section only → user reviews a real scientific-results summary → separately authorizes manuscript writing → formal manuscript sections can then be drafted. Failure / pause / pivot records evidence, invalid assumptions, restart conditions and reusable assets.

**WRITING_LOCKED is a manuscript-prose lock, not an outline-planning lock.** It prohibits automatic publication title, abstract, Introduction/Methods/Results/Discussion/Conclusion prose, finished captions and first draft until the two user decisions. A blueprint cannot grant prose permission. All images, plots, previews and diagrams additionally require the original user's explicit drawing request. Downloads, CPU/GPU, SEALED/CONFIRMATION, Task pivot, sharing, submission and spending remain separately controlled.

RWF should only provide a compact factual patch: relevant EXP/Run/Claim → exact source receipt and status → what changed / negative evidence → single next action → if necessary the affected H1/H2 plus missing evidence. Do not force migration, re-read all history, spawn writing agents, introduce a new CLI state, or mistake a source hash for independent science verification.

## Cold-start read order and stable references (no new phase)

- **Single entrypoint:** PD-RW AGENTS.md when PD-RW controls the scientific research; RWF AGENTS.md is the entry only for independent Forge work. In a PD-RW project, open RESEARCH_RECORD.md snapshot/current supported results/important negative routes/next action **before** reading its full experiment history. If the request changes the paper, load PAPER_BLUEPRINT.md planning snapshot and the impacted SEC_ID only. Open RWF STATE, DEV prediction files, experiment protocols and relevant specialized Skills only as demanded by the current blocker.
- **Source authority:** the user's actual original instruction and legitimate frozen source artifacts take precedence over both Markdown summaries. RWF read-only source-hash receipts are not scientific proof. Mark contradictory descriptions SOURCE_CONFLICT and check original Run/protocol rather than silently promoting the blueprint.
- **Stable identifiers:** preserve existing EXP/Run/Claim IDs. New meaningful attempts may be EXP-001 etc. Paper H1/H2 in the user's sense are Markdown H2/H3 under a unique document H1; stable SEC_ID identifies a subsection across heading renames/reordering. Do not rename existing C01 or vendor Run IDs for cosmetics. An outline section references original EXP/Run/Claim, legitimate split, unit and protocol; paper planning changes must not overwrite failed research history.
- **Partial updates:** after meaningful DEV work, update only the record's brief latest snapshot and append a factual experiment event in the record's final history section. Only scientific or venue changes materially affecting the outline warrant a local SEC_ID update. The project keeps two human-readable Markdown records and existing factual STATE/Run stores, **not a third memory ledger**.
- **Cold-start acceptance check:** a new agent should be able to identify the research question, best verifiable Run and its protocol, important failed/invalid attempts, the next legal step and required authorization, plus the relevant SEC_ID/evidence gap when applicable. Static tests only check structure and routing; they do **not** establish improved AI comprehension or measured token efficiency. A real controlled agent handoff comparison is required to substantiate those improvements.
