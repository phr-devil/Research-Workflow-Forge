# 05 | Algorithm implementation and feedback

Shared rules: [EXECUTION_POLICY](../../docs/EXECUTION_POLICY.md). Execution requires real Task, protected evaluator, eligible DEV data and actual authorization.

- Work in one coherent **DRAFT → DEBUG / IMPROVE → directed test → record** batch.
- **Default:** reuse or obtain a trustworthy simple matched-information baseline first; identify an observed unresolved error and the least expensive discriminating experiment. Increase architecture complexity only to test a distinct mechanism, satisfy a concrete deployment constraint, or address demonstrable capacity/temporal needs. Model size alone is not a scientific novelty claim. Diagnose the earliest engineering failure, repair locally and test affected interfaces; do not run unrelated full tests after every edit.
- **Scientific-evidence completion rule (not manuscript drafting):** before another expensive architecture/large run, check whether the existing credible result supports one distinguishable, scoped manuscript contribution with at most a few decisive missing tests. If yes, keep the best validated method and test the strongest directly relevant baseline, independent-group reliability, label/compute cost, or claim-matched confirmation **instead of tuning for global SOTA**. If no independent contribution survives closest-paper comparison, keep the engineering asset and seek a genuinely different Claim; do not pretend a positive DEV score itself proves publishability.
- Preserve task/protocol/data/code/evaluator IDs, raw stdout/predictions, SHA receipts, candidate parent and negative Runs. No cherry-picked seed or evaluator changes disguised as improvement.
- Current **bounded** engine: `python -m tools.experiment_runner` for opt-in grouped DEV dummy/logistic/forest; no arbitrary Agent-produced code or GPU. Then `core.cli record`, `core.cli compare` and explicit `core.cli champion`. `core.cli candidates` shows lineage, not a complete AIDE executor.
- **Q2 competitiveness check:** preserving a positive DEV increment does not finish the project. If its independent scientific value is weaker than the named Q2+ analogs, prefer one decisive evidence/novelty upgrade or credible task reframing; continue a more ambitious but bounded test when the expected value justifies its cost. Stop adding complexity when it cannot change the scientific Claim or credibility. Do not promise acceptance or start drafting.
- Once one defensible incremental Claim is supported on DEV, prioritize its most decisive comparator, cost measurement, limited ablation or group robustness over new architectures. Stop seeking global SOTA unless the chosen Claim depends on it. A method may trade a small honest accuracy loss for meaningful efficiency, with both reported and compared fairly.
- More runs are justified only by a different mechanism, unfair baseline, inadequate convergence, uncertainty or another decision-changing reason. If a fair simple model matches or exceeds a complex challenger, preserve the simple reference and diagnose the challenger at mechanism scope; do not run endless cosmetic hyperparameter searches. A valid negative routes to 06 rather than endless hyperparameter churn.

**External deep models:** when the built-in bounded CPU pilot is inadequate, follow [EXTERNAL_MODEL_EVIDENCE](../../docs/EXTERNAL_MODEL_EVIDENCE.md): delegate only within actual user authorization, retain original artifact hashes, and independently recompute DEV metrics only where standard evaluator supports the real problem. Do not fabricate a 'fully verified' Run from a checkpoint hash; large tasks may require a separately reviewed task-specific evaluator.

**High-upside algorithm mechanism exploration:** use [HIGH_VALUE_RESEARCH_ENGINEERING](../../docs/HIGH_VALUE_RESEARCH_ENGINEERING.md) §04–05 when existing baseline evidence exposes a meaningful gap. Consider at most 3 **distinct scientific levers** (legally available information, inductive bias, optimization/calibration, reliability policy, real deployment cost), keep one Champion and normally one active Challenger, choose the single most informative authorized DEV probe. A stronger temporal/physical model may be appropriate when a falsifiable unresolved bottleneck warrants it; do not confuse one failed short training or an easy small result with the upper bound on Q2/Q1 novelty. Borrow RD-Agent's experiment feedback and Optuna's pruning only inside actual budget; no automatic HPO/dependency install or holdout reuse. Negative runs persist; stop a mechanism when further trials cannot change the Claim.

**Post-algorithm micro-upgrade:** once the stable Champion exists and there is a meaningful potential new Claim, invoke [post-algorithm audit](../../docs/POST_ALGORITHM_SCIENCE_AUDIT.md) only on demand. Prefer existing verified group residuals and one distinguishing test over adding another network; if evidence is negative, preserve existing algorithm and summarize. No writing authorization follows from this audit.

**Next-step instruction rule:** when the next technical action is already authorized, directly provide one concise executable instruction using current Run/Task receipts and minimal verification. When more CPU/GPU/data/sealed access is needed, recommend and offer user choices but no execution prompt. See [NEXT_ACTION_POLICY](../../docs/NEXT_ACTION_POLICY.md).

**Handoff:** real RunRecord / NOT_RUN, compatible Champion comparison, mechanism-level observation and next discriminating action.

**v0.7:** Reject self-reported metric improvements: standard predictions must be independently re-evaluated against a SHA-pinned DEV source/frozen group split. External Codex/WorkBuddy scripts may produce predictions in separately controlled workspaces, then `adapters.agent_bridge` imports them without execution. `core.cli compare` now requires `--dir`; Champion preview includes provisional group-bootstrap uncertainty. Details only if needed: `docs/ARTIFACT_CONTRACT.md`.


**v0.8真实实证**：支持在SHA固定DEV组清单上核回归/事件预测的原始标签、样本覆盖及指标。不同K、合法预测时点、聚合口径或事件容差不属于公平Challenger比较；负Pilot优先复核评价/训练/可辨识性，再决定独立新机制。内置训练器仍只含有限分类CPU基线；不能虚称支持任意GPU Agent自主训练。

**Before expensive new mechanism (only when evidence exists):** identify an observed baseline failure, legitimate information/inductive-bias/optimization lever, and a distinct prediction testable with the smallest authorized run. If the model merely has more parameters, do not invent a new science hypothesis. Reuse verified group residual summary; if performance rises, still test fair strong simple alternatives and independent group/Task conditions.

**v0.10 hypothesis→Run:** On an evidence-supported candidate, link `hypothesis_id` to the existing Task/Experiment IDs and parent Run; keep exact protected evaluator and legal inputs. Do not substitute model-size variation for a distinguishing prediction. The separate Agent runs only authorized work; once a DEV Run has independently verified receipts, register exploration feedback in a NEW hypothesis-bank version, not as confirmed mechanism evidence.
